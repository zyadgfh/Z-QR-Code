# QR Menu — منيو QR وطلبات الترابيزة للمحلات الصغيرة

SaaS متعدد المحلات (multi-tenant): منيو رقمي لكل محل يفتحه العميل بمسح كود QR على الترابيزة، يبني طلبًا ويرسله، والمحل يستقبله لحظيًا في لوحة تحكم مع تنبيه صوتي متكرر. **عربي أولًا (RTL)** مع دعم الإنجليزية.

- طلبات **داخل المحل فقط** (dine-in) — بدون دفع أونلاين وبدون دليفري في هذه النسخة.
- تجربة **13 يوم** لكل محل، ثم قفل كامل حتى يدفع صاحب المحل (تحصيل يدوي، تفعيل من لوحة أدمن المنصة).
- أسعار الطلب تُحسب **من قاعدة البيانات على الخادم** — أي أسعار يرسلها العميل تُهمَل.
- كل عمليات البيانات تمر عبر الخادم (Express) — عزل المستأجرين مفروض في كود الخادم وليس في الواجهة.
- **الواجهة**: تصميم بطابع آبل — iOS زجاجي لحركات GSAP في صفحات العميل، macOS هادئ للوحتَي التحكم، مع احترام `prefers-reduced-motion`.
- **الأمان**: تقرير تدقيق شامل في [`docs/SECURITY.md`](docs/SECURITY.md) — ترويسات أمان، حدود معدل، بوابة إعداد أول أدمن تُغلق نهائيًا، تغيير كلمة المرور لكل الأدوار.

## بنية المشروع

```
├── server/            # Express API (CommonJS) — كل المنطق الآمن هنا
│   ├── app.js         #   تجميع التطبيق createApp()
│   ├── index.js       #   تشغيل كخدمة واحدة (Render): API + ملفات العميل
│   ├── db/            #   محوّلان بنفس الواجهة: memory (تطوير/تجربة) و firestore (إنتاج)
│   ├── services/      #   منطق الأعمال: shops, menu, orders, admin, ai
│   ├── routes/        #   auth / public / shop / admin
│   └── seed.js        #   بيانات ديمو
├── client/            # React + Vite + TypeScript + Tailwind v4
│   └── src/pages/     #   customer/ (منيو وسلة ومتابعة) · dash/ (لوحة المحل) · admin/
├── api/index.js       # نقطة دخول Vercel (serverless يلفّ نفس تطبيق Express)
├── tests/             # 28 اختبارًا (node:test) تغطي كل معايير القبول
├── firestore.rules    # قواعد تمنع وصول العميل مباشرة لقاعدة البيانات
└── vercel.json        # إعدادات نشر Vercel (ثابت + API)
```

## التشغيل المحلي

```bash
npm install           # يثبت server و client معًا (workspaces)
npm run build         # يبني client/dist
npm start             # يشتغل على http://localhost:8080 — وضع الذاكرة ببيانات ديمو
```

للتطوير المتزامن (إعادة تحميل فورية للواجهة):

```bash
node server/index.js           # طرفية 1: API على 8080
npm run dev:client             # طرفية 2: Vite على 5173 (proxy تلقائي لـ /api)
```

الاختبارات (28 اختبارًا):

```bash
npm test
```

> وضع الذاكرة (`DB_ADAPTER=memory`) يبدأ تلقائيًا ببيانات ديمو ولا يحتاج أي خدمات خارجية — مناسب للتجربة والاختبار والعرض الحي فقط.

## متغيرات البيئة

| المتغير | مطلوب؟ | الوصف |
|---|---|---|
| `DB_ADAPTER` | نعم | `memory` (تجربة) أو `firestore` (إنتاج) |
| `JWT_SECRET` | نعم في الإنتاج | سر توقيع الجلسات — سلسلة عشوائية طويلة |
| `PORT` | لا | افتراضي 8080 (Render يحدده تلقائيًا) |
| `FIREBASE_SERVICE_ACCOUNT_B64` | عند firestore | محتوى ملف service account JSON بترميز base64: `base64 -w0 serviceAccount.json` |
| `FIREBASE_STORAGE_BUCKET` | لا | اسم bucket (افتراضيًا `project_id.appspot.com`) |
| `GEMINI_API_KEY` | للاستيراد بالـ AI | مفتاح Google AI Studio — استخراج المنيو من صورة |
| `GEMINI_MODEL` | لا | افتراضي `gemini-3.5-flash-lite` |
| `CORS_ORIGIN` | لا | عند فصل الفرونت والباك على نطاقين: نطاق الفرونت |

## إعداد Firebase (الإنتاج)

المشروع يستخدم Firebase كقاعدة بيانات (Firestore) ومخزن صور (Storage) — **عبر الخادم فقط**، بدون Firebase Auth ولا SDK في المتصفح:

1. أنشئ مشروعًا على [console.firebase.google.com](https://console.firebase.google.com) (خطة Spark المجانية تكفي).
2. **Firestore Database** → إنشاء (Native mode) → أي منطقة قريبة.
3. **Storage** → إنشاء bucket.
4. انشر قواعد الأمان من الملفين في المستودع (`firestore.rules`, `storage.rules`) — أو من لوحة التحكم: Firestore/Storage → Rules والصقها. هي تمنع المتصفح تمامًا وتسمح بقراءة الصور العامة فقط.
5. Project Settings → **Service accounts** → Generate new private key → احفظ الملف.
6. حوّله base64 وضعه في متغير البيئة:
   ```bash
   base64 -w0 serviceAccount.json   # انسخ الناتج كاملًا
   ```
7. بذر بيانات ديمو + حسابات العمل (اختياري):
   ```bash
   DB_ADAPTER=firestore FIREBASE_SERVICE_ACCOUNT_B64=... npm run seed
   ```
   أو أنشئ أول محل من لوحة `/admin` مباشرة (هذا هو المسار الطبيعي — التسجيل ذاتي غير مفعّل بقرار من المالك).
8. **التحقق بعد النشر:** افتح `/api/health` — النجاح يعني `{"ok":true,"adapter":"firestore"}`، وأي مشكلة ستعيد رسالة عربية تخبرك بالضبط بالناقص (Firestore غير مُفعّل / بيانات الـ service account غير صحيحة).

> ملاحظات: كونفيج الويب (`firebaseConfig` بأسماء `apiKey`/`authDomain`…) هو إعداد تطبيق العميل و**لا يُستخدم** في بنيتنا — كل الاتصال من الخادم عبر الـ service account. المشاريع الجديدة اسم bucket فيها يظهر بصيغة `<project>.firebasestorage.app` — ضعه كما هو في `FIREBASE_STORAGE_BUCKET`.

## النشر

### Render (الأسهل — خدمة واحدة)

1. New → **Web Service** → اربط المستودع.
2. Build Command: `npm install && npm run build`
3. Start Command: `npm start`
4. أضف متغيرات البيئة: `DB_ADAPTER=firestore`, `JWT_SECRET`, `FIREBASE_SERVICE_ACCOUNT_B64`, (و`GEMINI_API_KEY` لاحقًا).
5. Health Check Path: `/api/health`.

### Vercel (نفس المستودع)

- اربط المستودع بـ Vercel وسيقرأ `vercel.json`: يبني العميل (`npm run build`) ويقدم `client/dist` كملفات ثابتة، وكل مسارات `/api/*` تذهب لـ `api/index.js` (نفس تطبيق Express كـ serverless).
- أضف نفس متغيرات البيئة في Project Settings.
- ملاحظات serverless: تحديد المعدل ضد السبام يعمل لكل نسخة (تقريبي)، وحد رفع الجسم 4.5MB (ضغط الصور في المتصفح يبقيها أقل من ذلك). للتجربة الكاملة بلا حدود استخدم Render، أو شغّل Vercel للواجهة وRender للـ API (ضع رابط الـ API في `VITE_API_BASE` ونطاق الواجهة في `CORS_ORIGIN` على الـ API).

## استيراد المنيو بالذكاء الاصطناعي (اختياري)

1. احصل على مفتاح مجاني من [Google AI Studio](https://aistudio.google.com/apikey).
2. ضعه في `GEMINI_API_KEY` وأعد النشر.
3. في لوحة المحل → المنيو → **«استيراد من صورة المنيو ✨»** → ارفع حتى 3 صور → راجع الأسماء والأسعار في جدول قابل للتعديل → **انشر**.
   لا يُنشر أي شيء تلقائيًا — النشر خطوة يدوية بعد المراجعة (قرار ثابت في المواصفات).

## قرارات معمارية (انحرافات موثقة عن المواصفات)

1. **Firebase بدل Supabase** (§11): قرار من المالك — يريحنا من Edge Functions ويشغّل على أي مزود (Render وVercel كما يريد المالك).
2. **وصول البيانات من الخادم فقط** بدل RLS من المتصفح: كل نداءات البيانات تمر عبر Express، فالعزل مفروض بنقطة واحدة (دوال الخدمات تتحقق أن كل مستند يخص محل صاحب الجلسة) — أقوى وأسهل اختبارًا، وقواعد Firestore تمنع المتصفح تمامًا كطبقة ثانية.
3. **مصادقة خاصة (JWT + scrypt) بدل Firebase Auth**: أقل خطوات إعداد للمحلات، ويعمل في وضع الذاكرة وفي كل بيئات النشر بنفس السلوك. الصلاحيات (`owner`/`staff`/`platform_admin`) تُفحص على الخادم في كل نداء.
4. **التحديث اللحظي بالاستقصاء (polling كل 4 ثوانٍ)** بدل listeners دائمية: يعمل على أي بيئة نشر (Render وserverless)، ولا يخفي أبدًا طلبًا معلقًا عند انقطاع الاتصال — وهذا شرط المواصفات §12. الاستقصاء بسيط ورخيص على حجم المحل الواحد.
5. العميل لا يرى مراحل العمل إطلاقًا — بعد القبول يظهر له الوقت المتوقع فقط، وتُحذف أسماء المراحل من API العميل نفسه.
